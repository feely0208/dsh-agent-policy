# 策略声明核对（dsh-agent-policy）

**什么时候用**：想知道一个 agent / 自动化项目**说好要做的事**和**代码里实际做的事**是不是一回事。
用户会说：「策略和实现对不上」「说好不出网的」「agent 权限声明在哪」「允许一切是不是有问题」「这个操作要不要人工确认」「帮我核对下策略文件」。

## 怎么用

```bash
dsh-agent-policy --root <项目目录>
```

## 怎么读结果

它只做一件事：**把声明和代码摆在一起比**。命中时按这个顺序想：

1. **声明不出网，代码里有网络调用**（`POLICY-EGRESS-PROMISE`）—— 先确认那处调用是不是漏删的调试代码、或者三方依赖带进来的；然后**改代码或改声明**，别留着对不上。
2. **声明要人工确认，代码却直接执行**（`POLICY-CONFIRM-MISSING`）—— 高风险动作（删除 / 转账 / 退款 / 发布）没有确认闸门，只差一次误判或一次提示注入。要么真接上确认，要么把声明删掉（但要想清楚删掉之后谁负责）。
3. **通配符放权**（`POLICY-WILDCARD-ALLOW`）—— `allow: "*"` 读起来像「已声明」，其实是「不限制」。这种最危险的地方在于它让评审的人以为边界存在。
4. **工具清单是空的**（`POLICY-DECL-EMPTY`）—— 写了字段没写内容，等于没声明。要么补全，要么明确写「本 agent 不调用任何工具」。
5. **完全没有策略文件**（`POLICY-NO-DECLARATION`）—— agent 的权限只存在于代码里，评审的人无从核对。补一份，哪怕只有几行。

## 报告里的 `notApplicable`

`POLICY-NO-DECLARATION` 只在含 agent 特征的目录上跑。如果报告显示它不适用，说明这个项目里没找到调模型 / 工具调用的迹象 —— **不是「检查通过了」，是「这条没跑」**。

## 不要做什么

- 不要把它当成「合规通过证明」—— 它只比对你给的两份材料，材料本身写错了它看不出来
- 不要因为「策略文件写得很规范」就放心 —— 这个工具存在的理由正是：规范的声明和实际的代码经常不是一回事
- 不要只改策略文件让告警消失 —— 那是最坏的一种「修复」
